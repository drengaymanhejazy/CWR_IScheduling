# تقرير جاهزية مستودع منصة إدارة الري والتسميد للانتقال إلى Kotlin

**التاريخ:** 28 تشرين الثاني/نوفمبر 2026  
**المشروع:** إدارة الري والتسميد في المزرعة  
**المستودع:** `CWR_IScheduling`  
**آخر إصدار واجهة منشور وقت إعداد التقرير:** `0167dbe`  
**حالة التقرير:** تقييم هندسي أولي قابل للمراجعة

## 1. الملخص التنفيذي

المستودع مناسب للانتقال إلى Kotlin من ناحية الفكرة، البيانات الأولية، والمحركات الحسابية التي تم بناؤها داخل النموذج HTML/JavaScript. لكنه غير جاهز للترحيل المباشر إلى تطبيق إنتاجي نهائي؛ فالترحيل الحرفي سيحمل معه بعض مشكلات تنظيم الواجهة، وتداخل مسؤوليات العرض والحساب والتخزين، ونقص الاختبارات الآلية.

التوصية هي اعتماد المستودع الحالي كـ **مرجع وظيفي ونموذج إثبات مفهوم**، ثم إنشاء طبقة مجال Kotlin مستقلة ومختبرة قبل بناء واجهة Android جديدة. لا يُنصح بتحويل صفحات HTML إلى شاشات Compose واحدًا لواحد قبل تثبيت العقود الحسابية والبيانية.

## 2. نطاق التقييم

يشمل التقييم:

- محرك الطقس وحساب البخرنتح المرجعي ET0 وفق FAO-56 Penman–Monteith.
- معاملات المحصول Kc وحساب ETc ومراحل النمو المحلية.
- ميزان ماء التربة والمحاكاة اليومية.
- المطر اليدوي والري الفعلي والمطر الفعال المؤقت.
- نموذج DIN لبيانات الحقل والتربة وطريقة الري.
- طبقة التوصية السمادية المرتبطة بملفات SoilFert.
- سجلات العمليات والتكاليف والحصاد والإنتاج.
- بنية التخزين المحلي الحالية.
- قابلية فصل المنطق عن الواجهة لتأسيس تطبيق Kotlin/Android.

لا يتضمن التقييم اعتمادًا زراعيًا نهائيًا لجرعات الأسمدة أو اعتمادًا تشغيليًا لبيانات إنتاجية غير موثقة.

## 3. ما هو جاهز وقابل لإعادة الاستخدام

### 3.1 المحركات الحسابية

يوجد أساس عملي قابل لإعادة البناء داخل Kotlin، ويشمل:

- تحويل بيانات الطقس إلى متغيرات تشغيلية.
- حساب ضغط البخار، الضغط الجوي، الإشعاع الفلكي، والرياح عند ارتفاع مترين.
- حساب ET0 مع تمييز البيانات الفعلية والبديلة والتوقعات والبيانات غير المكتملة.
- حساب Kc اليومي وفق أطوال L1 وL2 وL3 وL4.
- حساب ETc من العلاقة `ETc = ET0 × Kc`.
- تحديد حالة الموسم: قبل البداية، قائم، أو منتهٍ.
- حساب TAW وRAW من FC وWP وعمق الجذور وMAD.
- محاكاة رصيد ماء التربة يوميًا مع المطر والري الفعلي وكفاءة الري ومعامل التغطية.

هذه المكونات قابلة للتحويل إلى وظائف نقية Pure Functions، وهو الشكل الأنسب للاختبار وإعادة الاستخدام داخل تطبيق Android.

### 3.2 البيانات المحلية

المستودع يحتوي على قواعد محلية أولية مفيدة كنقطة انطلاق:

- المحاصيل السورية وقيم Kc وأطوال الأطوار وعمق الجذور.
- المواقع والمحافظات والإحداثيات المرجعية.
- خريطة الربط بين معرفات المحاصيل وملفات SoilFert.
- ملفات تعريف SoilFert ومستويات تشخيص N/P/K والمادة العضوية.
- عقود JSON لسجل العمليات والتكاليف وسجل الحصاد.
- وثائق DIN ومعمارية الإنتاج والتسويق.

ينبغي نقل هذه البيانات إلى ملفات موارد منظمة أو إلى جداول Room، مع الإبقاء على مصدر كل قيمة وحالتها: محلية، إرشادية، بديلة، أو تحتاج مراجعة.

### 3.3 منطق السجلات

سجلات العمليات والتكاليف والحصاد تحتوي على فصل مهم ينبغي الحفاظ عليه في Kotlin:

- المخطط والتقديري والفعلي حالات منفصلة.
- الإنتاج الخام منفصل عن القابل للتسويق والفاقد.
- السجلات مرتبطة بالحقل والموسم والمحصول.
- الاستيراد والتصدير يعتمدان على عقود JSON محلية.

## 4. ما يحتاج إلى إعادة بناء قبل أو أثناء الترحيل

### 4.1 فصل طبقات النظام

المنطق الحالي موزع داخل `app.js` ومرتبط بعناصر DOM والتخزين المحلي. قبل النقل يجب فصل الطبقات التالية:

1. **Domain:** المعادلات، الحالات، القواعد، والتحقق من القيم.
2. **Data:** قراءة JSON، Room، والاستيراد والتصدير.
3. **Repository:** مصدر موحد للمحاصيل والطقس وملف DIN وSoilFert.
4. **Application/ViewModel:** إدارة الحالة والأحداث وطلبات التحديث.
5. **UI:** شاشات Compose ومكونات العرض.

لا ينبغي أن تعرف محركات ET0 أو SoilFert أي شيء عن `TextField` أو `localStorage` أو عناصر HTML.

### 4.2 محرك التسميد

المحرك الحالي مفيد كنموذج إرشادي، لكنه يحتاج إلى تثبيت قبل اعتباره عقدًا نهائيًا:

- توثيق وحدة كل قيمة من تحليل التربة وطريقة الاستخلاص.
- فصل الربط المباشر عن الربط البديل وإظهاره للمستخدم.
- منع أي تعيين تلقائي لمحصول غير موثق في SoilFert.
- تثبيت أثر نمط الري على الملف المختار، خصوصًا للمحاصيل التي لها نسخ مروية وبعلية.
- تثبيت أثر المادة العضوية وعمر الأشجار ضمن قواعد موثقة.
- إضافة اختبارات لحالات N/P/K والمادة العضوية الناقصة أو خارج الحدود.
- إبقاء المخرجات إرشادية، مع رسالة صريحة تمنع اعتبارها وصفة تنفيذية نهائية دون مراجعة مختص.

### 4.3 الواجهة وتجربة الاستخدام

الواجهة الحالية تثبت وجود الوظائف، لكنها تحتاج إعادة تصميم قبل اعتبارها مرجعًا بصريًا لتطبيق Android. المشكلات التي ينبغي معالجتها في التصميم الجديد تشمل:

- تقليل الفراغات غير المفيدة في بطاقات مراحل النمو.
- منع تداخل بطاقات المحركات عند اختلاف عرض الشاشة.
- وضع المحصول والموسم في سياق مركزي واحد بدل تكرار المدخلات.
- جعل انتقال المستخدم واضحًا من إعداد الحقل إلى التربة والري ثم التوصية.
- تمييز المدخلات المطلوبة عن الاختيارية وعن القيم الافتراضية.
- عرض نتيجة SoilFert مع المحصول وطريقة الري وتحليل التربة في بطاقة واحدة مترابطة.
- تصميم مناسب للهاتف أولًا، مع قابلية استخدام المرشد الزراعي على شاشة أكبر.

ينبغي ألا يُنقل التخطيط الحالي حرفيًا إلى Compose؛ الأفضل بناء نظام مكونات جديد مستند إلى نفس الهوية التشغيلية.

### 4.4 التخزين المحلي

يعتمد النموذج الحالي على `sessionStorage` و`localStorage`. في Kotlin يجب اعتماد تخزين صريح، مثل:

- Room للحقول والمواسم وملفات DIN وسجلات العمليات والحصاد.
- DataStore للإعدادات الصغيرة مثل المنطقة الافتراضية وتفضيلات العرض.
- طبقة استيراد وتصدير JSON مع إصدار Schema واضح.
- ترحيلات Migration لكل تغيير في بنية البيانات.
- سياسة نسخ احتياطي محلي قبل أي ترقية كبيرة.

## 5. مصفوفة الجاهزية

| المجال | الحالة الحالية | القرار للترحيل |
|---|---|---|
| ET0 وفق FAO-56 | جيد كنموذج أولي | ينقل بعد كتابة اختبارات مرجعية |
| Kc وETc | جيد وقابل للفصل | ينقل إلى Domain Core |
| أطوار النمو | البيانات موجودة، العرض يحتاج صقلًا | تثبيت عقد المرحلة ثم إعادة تصميم العرض |
| ميزان ماء التربة | موجود وقابل للاختبار | ينقل بعد تثبيت الوحدات والحالات الحدية |
| الطقس الفعلي والتوقعات | موجود مع مصدر بديل للإشعاع | ينقل خلف WeatherRepository |
| نموذج DIN | موجود في JSON وواجهة HTML | يعاد نمذجته كـ FieldProfile/SoilAnalysis/IrrigationProfile |
| SoilFert | ربط إرشادي أولي | يحتاج اختبارات وتثبيت سياسة الربط |
| العمليات والتكاليف | عقد محلي وسجل واجهة | ينقل إلى Room بعد تثبيت المخطط |
| الحصاد والإنتاج | عقد محلي وسجل واجهة | ينقل مع فصل الخام والتسويقي والفاقد |
| التخزين | Local/session storage | يستبدل بـ Room وDataStore |
| الواجهة | إثبات مفهوم غير نهائي | إعادة تصميم Compose |
| الاختبارات | فحوص syntax وJSON أساسًا | إضافة اختبارات وحدات وتكامل |
| الجاهزية لتطبيق إنتاجي | غير جاهز | يتطلب مرحلة تنظيم واختبار |

### المبدأ الأهم

يجب أن تقبل المحركات نماذج Kotlin وتعيد نتائج Kotlin، مثل:

```kotlin
val result = soilWaterBalanceEngine.simulate(
    profile = fieldProfile,
    weather = weatherSeries,
    irrigation = actualIrrigation
)
```

ولا ينبغي أن تقرأ المحركات الحقول من الشاشة أو أن تعدل قاعدة البيانات مباشرة.

## 7. خطة الانتقال المقترحة

### المرحلة الأولى: تثبيت العقد

- تثبيت أسماء الحقول والوحدات والأنواع.
- تحديد القيم الإلزامية والاختيارية وحدود التحقق.
- توثيق مصدر كل معامل زراعي.
- تثبيت حالات الربط في SoilFert.

### المرحلة الثانية: استخراج Domain Core

- نقل ET0 وKc وETc إلى Kotlin خالص.
- نقل ميزان الماء والمحاكاة اليومية.
- نقل تشخيص SoilFert دون واجهة.
- كتابة اختبارات مرجعية تقارن النتائج مع النسخة الحالية.

### المرحلة الثالثة: التخزين

- إنشاء Room entities وDAOs.
- بناء Repository للمحاصيل والتربة والري والتسميد.
- إضافة استيراد وتصدير JSON.
- إضافة Migration versioning.

### المرحلة الرابعة: واجهة Compose

- شاشة إعداد الحقل والموسم والمحصول.
- شاشة التربة والري في مسار واحد.
- شاشة نتائج الطقس وET0/Kc/ETc.
- شاشة ميزان ماء التربة.
- شاشة SoilFert مرتبطة تلقائيًا بالمحصول وطريقة الري والتحليل.
- شاشات العمليات والتكاليف والحصاد.

### المرحلة الخامسة: المقارنة والقبول

- تشغيل نفس المدخلات في HTML وKotlin.
- مقارنة ET0 وKc وETc وTAW وRAW ونتائج SoilFert.
- توثيق أي فروق مقصودة.
- اختبار الهاتف بأحجام شاشة مختلفة.
- اعتماد نسخة تجريبية داخلية قبل أي نشر عام.

## 8. معايير الجاهزية قبل إعلان النسخة الإنتاجية

لا تُعلن نسخة Kotlin إنتاجية قبل تحقق الشروط التالية:

- وجود اختبارات وحدات للمحركات الحسابية الأساسية.
- تطابق نتائج ET0 وKc وETc مع حالات مرجعية موثقة.
- تطابق ميزان الماء مع حالات مطر وري وعجز ابتدائي مختلفة.
- اختبار SoilFert للمحاصيل المباشرة والبدائل والمحاصيل غير المدعومة.
- عدم وجود تكرار لإدخال المحصول أو طريقة الري بين المحركات.
- نجاح الاستيراد والتصدير مع الحفاظ على إصدار المخطط.
- اكتمال حالات الخطأ والقيم الناقصة.
- عمل الواجهة على الهاتف دون تداخل أو فراغات كبيرة غير مبررة.
- تمييز القيم الفعلية والتقديرية والتوقعات والإرشادية بوضوح.
- توفير نسخ احتياطي محلي قبل ترقية قاعدة البيانات.

## 9. القرار النهائي

**المستودع جاهز لبدء مرحلة الترحيل المنظمة إلى Kotlin، وليس جاهزًا للترحيل المباشر إلى تطبيق إنتاجي نهائي.**

الخطوة الصحيحة التالية هي إنشاء Domain Core مستقل واختباره، وليس البدء بتقليد الواجهة الحالية في Compose. هذا المسار يحافظ على العمل الحسابي المنجز، ويمنع نقل مشكلات العرض والتخزين والربط إلى التطبيق الجديد.

ويُقترح إبقاء نسخة HTML الحالية كمرجع مقارنة وتشغيل تجريبي إلى أن تجتاز نسخة Kotlin اختبارات التطابق الوظيفي.
