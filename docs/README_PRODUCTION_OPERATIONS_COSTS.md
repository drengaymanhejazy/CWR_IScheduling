# README — سجل العمليات والتكاليف

## 1. الغرض

يعرّف هذا الملف طريقة استخدام نموذج سجل العمليات والتكاليف في منصة الري وجدولة الري للمحاصيل والأشجار المثمرة. النموذج هو طبقة إنتاج واقتصاد فوق طبقات الطقس والري والتسميد؛ ولا يغيّر حسابات `ET0` أو `Kc` أو `ETc` ولا يحول التوصية السمادية إلى فاتورة فعلية.

الملف المحلي المرجعي هو:

```text
data/production_operations_costs_v0.1.json
```

النموذج الحالي قالب محلي قابل للتصدير والاستيراد لاحقًا. لا توجد فيه أسعار أو تكاليف افتراضية، وتبقى السجلات الفعلية منفصلة عن التخطيط والتقدير.

## 2. موقعه ضمن المشروع

```text
الحقل + الموسم + المحصول
          │
          ├── الطقس و ET0 / Kc / ETc
          ├── ميزان الماء وسجل الري الفعلي
          ├── محرك التوصية السمادية
          └── سجل العمليات والتكاليف
                 │
                 ├── خطة وتقدير
                 ├── تنفيذ فعلي ومصدر
                 └── مؤشرات التكلفة والاقتصاد
```

يجب أن يرتبط كل سجل على الأقل بـ `field_id` و`season_id`. ويضاف `crop_id` عندما يكون المحصول معروفًا في قاعدة المحاصيل المحلية.

## 3. البنية العامة للملف

يحتوي الملف على الأجزاء التالية:

| الجزء | الوظيفة |
|---|---|
| `schema_version` | إصدار عقد البيانات |
| `data_policy` | سياسات الفصل بين الفعلي والتقديري وقواعد العمل محليًا |
| `identity` | هوية الحقل والموسم والمحصول والمساحة |
| `allowed_values` | القيم المسموح بها للأنواع والحالات والوحدات |
| `records` | قائمة سجلات العمليات والتكاليف، وتبدأ فارغة |
| `record_contract` | شرح الحقول لكل سجل |
| `validation_rules` | قواعد التحقق قبل الحفظ أو الحساب |
| `empty_record_template` | قالب سجل جديد |
| `conventions` | صيغ التاريخ والوحدات وسياسة العملة |

## 4. دورة استخدام السجل

### الخطوة 1: تحديد السياق

قبل إضافة سجل، يجب تحديد:

- معرف الحقل `field_id`.
- معرف الموسم `season_id`.
- معرف المحصول `crop_id` إن توفر.
- المساحة ووحدتها في بيانات الموسم.

لا يفترض النموذج أن المساحة بالدونم تلقائيًا؛ يمكن أن تكون بالمتر المربع أو الدونم أو الهكتار وفق سجل الموسم.

### الخطوة 2: اختيار نوع العملية والمدخل

يتم اختيار `operation_type` للعملية، مثل:

- `land_preparation`: تجهيز الأرض.
- `planting`: الزراعة.
- `irrigation`: الري.
- `fertilization`: التسميد.
- `spraying`: الرش.
- `harvesting`: الحصاد.
- `transport`: النقل.
- `storage`: التخزين.

ويتم اختيار `input_type` للمدخل أو الخدمة، مثل `fertilizer` أو `labor` أو `machinery` أو `water`.

يمكن أن يكون نوع العملية ونوع المدخل مختلفين؛ مثلًا عملية `fertilization` ومدخلها `fertilizer`، أو عملية `land_preparation` ومدخلها `machinery`.

### الخطوة 3: تحديد حالة السجل

| الحالة | الاستخدام |
|---|---|
| `planned` | عملية أو تكلفة مقررة قبل التنفيذ |
| `estimated` | قيمة تقديرية أدخلها المستخدم أو المرشد أو النموذج |
| `actual` | حدث فعليًا وله إدخال أو مصدر |
| `cancelled` | ألغي ولا يدخل في المؤشرات الحالية |
| `superseded` | استبدل بتصحيح لاحق، ويحتفظ به لأثر التدقيق |

لا تحذف السجل التقديري عند تسجيل الفعلي؛ يحتفظ النظام بكليهما للمقارنة بين المخطط والمنفذ.

### الخطوة 4: إدخال الكمية والتكلفة

كل كمية تحتاج إلى `unit`، وكل تكلفة نقدية تحتاج إلى `currency`.

الحقول الحسابية الأساسية:

```text
subtotal = quantity × unit_price

total_cost = subtotal + additional_cost − discount
```

إذا كانت التكلفة غير نقدية أو غير معروفة بعد، يمكن ترك السعر والتكلفة فارغين مع توضيح ذلك في `notes`، ولا يجوز اعتبار الفراغ صفرًا عند التحليل.

### الخطوة 5: تسجيل المصدر

يحدد `source_type` مصدر السجل، مثل:

- `user`: إدخال مباشر من المستخدم.
- `invoice`: فاتورة أو مستند شراء.
- `advisor`: إدخال أو تقدير المرشد الزراعي.
- `local_table`: جدول محلي موثق.
- `history`: سجل موسم سابق.
- `model`: ناتج نموذج تقديري.

يستخدم `source_ref` لتسجيل رقم الفاتورة أو اسم الملف أو المرجع الذي يسمح بالمراجعة.

## 6. مثال هيكلي غير فعلي

المثال التالي يوضح شكل سجل، لكنه لا يقدم سعرًا أو تكلفة أو كمية زراعية حقيقية:

```json
{
  "operation_id": "<معرف-محلي>",
  "field_id": "<معرف-الحقل>",
  "season_id": "<معرف-الموسم>",
  "crop_id": "<معرف-المحصول>",
  "operation_type": "fertilization",
  "input_type": "fertilizer",
  "description": "إضافة سماد مرتبطة بسجل التوصية",
  "event_date": "YYYY-MM-DD",
  "planned_or_actual": "estimated",
  "record_status": "estimated",
  "quantity": null,
  "unit": "kg",
  "unit_price": null,
  "currency": null,
  "subtotal": null,
  "additional_cost": 0,
  "discount": 0,
  "total_cost": null,
  "cost_basis": "direct",
  "allocation_method": "none",
  "source_type": "advisor",
  "source_ref": null,
  "linked_record_ids": [],
  "notes": "يستكمل بعد إدخال الكمية والسعر الفعليين",
  "created_at": null,
  "updated_at": null

```

القيم بين الأقواس الزاوية توضيحية وليست قيمًا صالحة للحفظ كما هي.

## 7. تصنيف التكاليف

### التكلفة المباشرة `direct`

تكلفة يمكن نسبتها مباشرة إلى الموسم، مثل كمية سماد اشتريت للمحصول أو أجور عمالة منفذة في الحقل.

### التكلفة الموزعة `allocated`

تكلفة مشتركة بين أكثر من حقل أو موسم. يجب تحديد طريقة التوزيع في `allocation_method`، مثل:

- `area`: حسب المساحة.
- `hours`: حسب ساعات استخدام الآلة.
- `quantity`: حسب كمية الاستخدام.
- `custom`: قاعدة يشرحها المستخدم في `notes`.

### التكلفة الضمنية `imputed`

قيمة تقديرية لأغراض التحليل، مثل تقدير عمل الأسرة أو استخدام أصل مملوك. لا تعرض كتكلفة نقدية فعلية إلا مع وسم واضح.

## 8. العلاقة مع الري والتسميد

يمكن ربط سجل العملية بسجلات أخرى عبر `linked_record_ids`، مثل:

- سجل ري فعلي يومي.
- سجل إضافة سماد.
- معرف توصية SoilFert.
- سجل تشغيل آلة أو مضخة.

هذا الربط لا يغير نتيجة محرك الري أو محرك التسميد. الغرض منه تفسير التكلفة الفعلية وربط العملية المنفذة بالتوصية أو الحساب السابق.

## 9. المؤشرات التي يمكن اشتقاقها لاحقًا

بعد اكتمال سجل الإنتاج والحصاد والبيع، يمكن استخدام سجلات التكلفة في:

```text
التكلفة الإجمالية = مجموع total_cost للسجلات الفعلية غير الملغاة
تكلفة المساحة = التكلفة الإجمالية ÷ مساحة الموسم
تكلفة الوحدة القابلة للتسويق = التكلفة الإجمالية ÷ الإنتاج القابل للتسويق
سعر التعادل = التكلفة المؤهلة ÷ الإنتاج القابل للتسويق
صافي الهامش = صافي الإيراد − التكلفة المؤهلة
```

يجب إظهار العملة ووحدة المساحة ووضع البيانات بجانب كل نتيجة. عند نقص الإنتاج أو السعر أو التكلفة، تعرض النتيجة «غير قابلة للحساب» بدل الصفر.

## 10. قواعد عدم الخلط

- لا تخلط المخطط بالفعلي.
- لا تعتبر التقدير حقيقة.
- لا تحذف التقدير عند تسجيل الفعلي.
- لا تعتبر التكلفة غير المدخلة صفرًا.
- لا تجمع عملات مختلفة دون تحويل موثق.
- لا تجمع وحدات مختلفة دون معامل تحويل موثق.
- لا تستخدم سعرًا سوقيًا كتسوية بيع فعلية.
- لا تُنشئ سعرًا أو تكلفة من دون مصدر أو وسم تقديري.
- لا تدخل السجلات `cancelled` و`superseded` في المؤشرات الحالية.

## 11. التحقق محليًا

من مجلد المشروع:

```bash
python3 -m json.tool data/production_operations_costs_v0.1.json

git diff --check
```

الملف JSON صالح عندما ينتهي الأمر الأول دون رسالة خطأ. أما اكتمال الحقول وقواعد الأعمال فيتحقق داخل التطبيق عند بناء نموذج الإدخال.

## 12. سياسة التخزين الحالية

النسخة الحالية من المنصة ثابتة وتعمل محليًا في المتصفح. لذلك:

- لا تعتبر `records` قاعدة بيانات مشتركة بين الأجهزة.
- يجب توفير تصدير واستيراد JSON قبل الانتقال إلى backend.
- يجب الاحتفاظ بنسخة من الملف المصدر عند كل تصدير مهم.
- لا ينشر الملف تلقائيًا ولا يرفع إلى GitHub بيانات الحقول أو الفواتير الفعلية.

عند بناء واجهة الإدخال لاحقًا، تستخدم هذه الوثيقة مع:

```text
data/production_operations_costs_v0.1.json
docs/PRODUCTION_MARKETING_ARCHITECTURE.md
docs/production_marketing_schema.sql
```
